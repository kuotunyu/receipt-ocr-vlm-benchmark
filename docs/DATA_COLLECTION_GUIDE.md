# 資料收集指引

> ⚠️ **本指引描述的「自行拍照 + 人工標註」流程最終未被採用**——實際評估改用零人工標註的
> 雙軌方案（45 張合成繁中 + 45 張 SROIE 真實英文收據），詳見 `plan.md` 的「資料策略 pivot」
> 與 `EVAL_REPORT.md`。本文件與底下的標註工具（`annotator/`）、`scripts/make_splits.py`
> 皆保留備用——之後若想真的補拍台灣發票照片，這條路線隨時可以接回來用。

目標：45 張自建繁體中文測試集（電子發票證明聯為主 ~35 張、傳統/手寫收據 ~10 張），
切為 dev 10 / test 35（`scripts/make_splits.py`）。**prompt 與 fuzzy 閾值只准在 dev 上調**，
test set 定案後不再回頭調整任何管線參數。

## Diversity Matrix（目標配比，45 張）

錯誤分析的價值來自資料本身的多樣性——每種挑戰都要有樣本，否則 EVAL_REPORT 的
「失敗模式」章節會沒東西寫。拍照時對照下表勾選，避免全部拍成理想光線下的乾淨收據。

| 挑戰類型 | 目標張數 | 說明 |
|---|---:|---|
| 清晰基準（無額外挑戰） | 12 | 平放、光線均勻、無皺摺——建立兩條管線的準確率上限 |
| 熱感紙褪色（存放數週以上的舊發票） | 8 | 傳統 OCR 二值化最大挑戰，也是最貼近真實場景的案例 |
| 皺摺 / 摺痕 | 6 | deskew 之外的幾何變形，測試前處理韌性 |
| 旋轉 / 傾斜拍攝（>10°） | 6 | 直接測試 deskew 的價值（Phase 4 消融實驗的主角之一） |
| 模糊（手震或對焦不準） | 4 | 測試兩條管線對低品質輸入的降級行為 |
| 含手寫字（收據上手寫品項/金額） | 5 | 傳統 OCR 弱項，VLM 的潛在優勢場景 |
| 含印章遮擋（部分文字被印章蓋住） | 4 | 兩條管線都難，看誰的降級更「優雅」（如給出 null 而非亂猜） |

同一張照片可以同時符合多個類別（如「旋轉+褪色」），不需要湊到 45 張的嚴格加總，
以上是「至少要涵蓋」的張數而非互斥分類。

## 拍攝規範

- **格式**：JPG 或 PNG；若手機預設存 HEIC，請先轉存為 JPG 再放入 `data/raw/`
  （Windows「照片」App 另存新檔即可轉檔）。
- **解析度**：長邊 ≥ 1600px 即可（現代手機預設拍攝解析度都遠超過此門檻，不必特別調整）。
- **命名**：檔名不重要，程式以檔名排序決定顯示順序；建議用 `receipt_001.jpg` 這類流水號方便自己管理。
- **內容框取**：文件本體盡量佔滿畫面，但不要裁切到任何你預期要抽取的欄位（含品項列表底部的總計）。
- **一張照片一份文件**：不要多張收據疊拍。

## 隱私與遮罩流程

電子發票證明聯上常帶有**載具條碼**（一維/二維）與**會員載具資訊**，收據上可能有**姓名/電話**。
原始照片、標註 JSON 與資料切分檔依 `.gitignore` 規則都不會進 repo；若要在
README/EVAL_REPORT 放範例截圖：

1. 從 `data/raw/` 複製一份到 `docs/examples/`（不要動原始檔）。
2. 用小畫家或任何影像編輯工具，對載具條碼/會員資訊/個人姓名電話畫實心色塊遮蓋。
3. 確認遮蓋後的檔案看不出任何可識別個資或可用的條碼，才放進 `docs/examples/` 提交。
4. Ground truth JSON（`data/labels/`）仍可能包含店名、統編、買受人統編或與影像可配對的資訊，
   因此與 `data/splits.json` 一併只留在本機；公開版只放 `results/official/` 的去識別化聚合指標。

## 標註流程

1. 把當批照片丟進 `data/raw/`。
2. 啟動標註工具：

   ```powershell
   .venv\Scripts\python -m uvicorn annotator.main:app --port 8010
   ```

   開啟 http://localhost:8010
3. 每張照片：看圖 → 點「OCR 預填建議」省打字 → **逐欄核對/修正**（不要照單全收，OCR 會錯，
   尤其是店名字體與模糊/褪色案例）→ 存檔（Ctrl+S）。
4. 全部標完後執行 `scripts/make_splits.py` 產生 `data/splits.json`（dev 10 / test 35，隨機但固定
   種子以利重現）。
